# H-04 300 s 分布采集与 dropout 时长字段缺陷

日期：2026-11-07。范围：32 GB 普通卡、零输出 300 s 正常日志；发现并修复 ULog dropout 时长饱和为 65535 ms 的软件缺陷。**本轮不作为 H-04 通过证据**，修复后的板载复测待回装。

## 采集结果

- source=`a17a2d35bab6f05a`，COM4，disarmed；`logger start/sync/stop` 均 `accepted=true`，结束 status=Disabled。
- 采集前后 165 项参数逐项一致；未设参/保存/清故障/重启。
- 文件 7,528,960 B / 300.378 s / 25.06 kB/s；141,989 条记录、298 次 flush；正常记录丢失 32 条（0.0225%），事件丢失 0；队列高水位 80,416 B；pyulog 完整解析。
- `errors` 采集前后均为 5。该计数只由会话/管理失败递增；5 次发生在本上电周期内先前的只读下载尝试，本次 300 s 写入期间没有新增，status 始终为 Ready。

## 发现：6/12 个 dropout 时长饱和

ULog 中 12 个 dropout 标记：`65535, 5, 5, 65535, 65535, 5, 5, 65535, 65535, 5, 65535, 6` ms。

- 6 个 65535 是 u16 上限饱和，合计声称 393 s 丢失，超过 300 s 时间线，自相矛盾。
- 交叉核对：gyro/accel 最大记录间隔 **10.856 ms**，无任何 >100 ms 空洞；32 条丢失记录按 197.5 Hz 也只对应约 68 ms 累计量级。真实停顿不可能达到 65.5 s。
- 结论：饱和值是可重复的软件上报缺陷，不是实际数据丢失。

## 根因与修复

`log_queue.rs` 用 `wrapping_sub` 计算 `now_ms - start_ms`。生产者传入的是各自采样时间戳，估计器/参数等记录与后续传感器记录可能存在数毫秒的先后交错；一旦 `now < start`，无符号回绕成约 42.9 亿 ms，再被 `min(65535)` 截成 65535。

修复：改用 `saturating_sub`，并把该场景固化为 host 用例 `dropout_duration_does_not_wrap_on_out_of_order_timestamp`（回绕时上报 0 ms，而不是 65535）。

复验：`cargo fmt --all -- --check` 通过；host `cargo test --lib` **188 passed**；host 与普通 H753 Clippy（`-D warnings`）通过；`tools/build_firmware.ps1` 打包 source=`f1825489b4f35661`，raw/padded=`1124928/1124928 B`，static RAM=`254224 B`，最大入口帧=`11496 B`。
