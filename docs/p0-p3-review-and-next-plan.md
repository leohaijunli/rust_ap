# P0–P3 方案评估与下一步建议

日期：2026-11-07。依据：[原方案](<Rust 四旋翼科研飞控 P0–P3 兼容与实施方案.md>)、[现行计划](../plan.md)、[当前状态](../TODO.md)、当前源码与[本次回装](acceptance/p1/20261107-current-firmware.md)。

**结论：科研四旋翼、Rust/Embassy、标准协议和可替换算法的方向可采纳，但原分期不能直接作为实施顺序。当前是已运行的数据链/估计基础，不是最小可飞闭环。** 本文是评估建议，不自动替代现行范围、必要测试或非零输出授权。

## 2. 原方案必须调整的内容

1. **阶段名不能复用现有含义。** 新方案 P0=可飞、P1=导航，与现行 P0=基线/P1=bring-up 等不同。产品路线可以另命名；实施与验收仍映射到现有 M1/P5/P6，不能把历史已完成的 P0/P1 等同于可飞阶段完成。
2. **日志、必要校准和恢复前置。** IMU 方向/偏置、RC 标定、真实电源监测、控制/输出/故障日志和可靠刷回必须在首飞前具备。可以推迟完整 QGC 校准向导，不能推迟校准本身。只做四旋翼，不引入无实际需求的空速、冗余 IMU或其他板型。
3. **PX4 身份不是“几乎零迁移”。** 固定 PX4 与工程师实际 QGC 版本，逐项记录“已支持/无数据/拒绝/待验”。参数同名时单位、范围和生效行为也要一致；不添加无作用参数迎合界面。当前先补 Quadrotor 类型与真实 SYS_STATUS present/enabled/health；未实现的模式/解锁继续拒绝。
4. **不发伪定位或伪执行器数据。** LOCAL_POSITION_NED 没有有效位，GLOBAL_POSITION_INT 也不能靠额外文本让无效位置可靠失效。保留现有无效/陈旧即停发策略，用 ESTIMATOR_STATUS/STATUSTEXT 表达能力。RC/SERVO 只在有真实对应来源时发布，不能把 CAN ESC 输出伪装成 PWM 测量。
5. **保持已确认范围。** 当前 H-RTK GNSS 使用 DroneCAN；“仅 ESC”会切掉现有导航来源，建议改为“ESC + 指定 H-RTK，不扩展通用外设”。2026-11-06 已明确删除无 GNSS 第二实例；保留单 Runtime 的降级/有效性，不恢复 component 197 或并行导航实例。改变这两项需工程师另行确认。
6. **failsafe 要按可用能力定义动作。** 无可靠高度/位置与降落控制器时不能承诺自动降落；地面锁定与空中失效不是同一动作。基线控制器回退还要求姿态、RC、执行器和基线本身健康。INA219 当前测独立支路，不能直接作为动力电池低压保护依据；真实动力电池监测方案是首飞前输入。
7. **定位、任务、Offboard 分门实施。** 先稳定手动姿态，再验证真实导航/原点/高度/航向与接管，之后才做 Home/RTL/任务。任务不能只按消息清单实现：还需上传/下载、重试/超时、mission_type、清除限制和部分任务提交规则。建议把基础任务从现行 P6g 对 INDI/NMPC 等研究阶段的依赖中拆出，仅依赖合格的位置控制、安全与链路；这是待确认的计划调整，不自动提前实施。Offboard/实验控制必须走同一输出仲裁，禁止算法直接写 ESC。
8. **按风险定测试，不按时长替代安全证明。** 沿用必要测试与历史结果，不自动重新加入每轮 1 小时/30 分钟压测。新控制路径另定周期/WCET、数据年龄、总线预算、丢控/停转/接管门；M1 的 5 分钟联合运行不是耐久或飞行验收。PlotJuggler/Flight Review 兼容须实际打开一份日志，不能由 pyulog 解析替代。

## 3. 建议执行顺序

| 顺序 | 对应现有阶段 | 本轮或下一轮目标 | 放行依据 |
| --- | --- | --- | --- |
| 0 | 基线 | 当前普通包回装、记录真实状态；固定兼容版本 | 本次已完成烧录/只读核对；QGC 版本仍需工程师确认 |
| 1 | P2/P3/P7 软件补齐 | Quadrotor HEARTBEAT、真实 SYS_STATUS 健康位、能力矩阵；保留拒绝 ARM/模式 | 健康/陈旧/缺传感器映射用例、普通构建；一次 QGC 用户可见核对 |
| 2 | PL-a/P4b-a/P2/P3/P4b-g/P4 | 按 H-04→H-02→H-03→H-10 补卡时延/故障、ESC 映射与零输出、双链路/参数保存、GNSS/授时，再收口 IMU 六面/校准/故障与 baro 实物项 | 每门一次正常与关键失败路径；先核对当前无 CAN/INA 应答及 IO Timeout，不猜硬件原因 |
| 3 | M1 | 一次 5 分钟零输出全数据链联合运行 | 各前置门通过；CPU<50%、共享栈 untouched≥16 KiB、周期/年龄/队列达标；dropout 按 H-04 预定窗口判定 |
| 4 | P5a/P5b、H-06/07 | 唯一输出仲裁、限时授权/撤销、过期/NaN/丢 RC/丢 ESC/总线故障锁定与恢复不自动解锁；只实现一种已确认 RC；补动力电池输入、看门狗和预检 | host 门后由工程师明确授权拆桨/限流台架；覆盖停转与接管，不默认开放 QGC 电机测试 |
| 5 | P6 | 一个基线速率/姿态控制器 + Quad X 分配；先 Acro/Stabilized，记录参考/误差/积分/饱和/输出 | 核心回放、积分抗饱和/复位/非法输入用例、实际闭环时序与台架；首飞另行授权，不由 M1 放飞 |
| 6 | 完整 E7 / P6c / P6d；P6g 依赖调整待确认 | 真实导航资格→高度/位置模式→Home/RTL→基础任务 | 只开放真实观测支持的模式；缺 mag/range 不填零；模式降级、任务往返/超时与接管分别验收；任务顺序变更先由工程师批准 |
| 7 | 后续科研/配置阶段 | 影子运行→受保护切换/Offboard、QGC 校准/执行器 GUI、教程和发布 | 基线先合格；超时/来源/坐标/限幅和失败回退有证据；沿用标准构建与 CI |

**最近的一项软件工作建议是第 1 行，而不是控制器或新 EKF 优化。硬件主线仍是第 2 行；未过门不进入非零输出。** 本次只完成评估，没有实施这些软件改动。

## 4. 工程师需要补充的决策

- 固定实际使用的 QGC 版本；确认保留现有 DroneCAN H-RTK、单估计器与 M1 数据链首目标。若改为手动可飞首目标，GNSS 可作为后续导航依赖，但要正式修订当前阶段关系，不能默默删除已有支持。
- 是否批准基础任务与 INDI/NMPC 等研究阶段解耦；在确认前不改现行 P6g 依赖。
- H-04：卡型号、写延迟分布和允许 dropout 窗口；H-02/03/10：ESC/CAN、TELEM1 与 GNSS 实物输入。
- H-06/07：RC 协议/接线、动力电池监测、台架授权/限幅/时限、撤销/接管判据。以 CAN ESC 为首输出路径，不同时开展 PWM/DShot 或 IO Rust 重写。
